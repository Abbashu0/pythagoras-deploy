# Pythagoras project context

Pythagoras is an Arabic study product with two product surfaces:

- Student: `public/pythagoras/`, served at `/`.
- Admin: `src/app/admin/`.

The content-platform master plan supersedes the earlier no-backend restriction. M1 provides a local Next.js server foundation backed by SQLite + Drizzle under `src/server/content/`, with committed migrations in `drizzle/`. Runtime data is configured by `PYTHAGORAS_DATA_DIR`; its safe Windows fallback is `%LOCALAPPDATA%\Pythagoras\data`. Runtime databases and assets must never be committed.

M2 adds durable local Admin identity under `src/server/admin-auth/`: first-run OWNER setup, Argon2id password hashes, opaque server-side sessions, OWNER/ADMIN authorization helpers, protected Admin routes, and safe actor attribution. Admin authentication never uses browser storage or JavaScript-readable tokens. The setup and login pages are `/admin/setup` and `/admin/login`; all other `/admin` routes require an active server session.

M3 implements local `AssetStorage` and the Asset domain under `src/server/assets/`. Asset metadata is SQLite-backed; immutable binary objects live in content-addressed SHA-256 paths under `<PYTHAGORAS_DATA_DIR>/storage/objects/`. Admin Asset APIs are authenticated and derive creator attribution from the server session.

M4 adds the operational Admin Asset Library at `/admin/library`: authenticated multi-file uploads, server-side search/filter/sort/pagination, inventory statistics, grid/list browsing, safe previews/downloads, creator details, and on-demand integrity checks. The library never exposes filesystem paths or storage keys. Legacy browser images remain untouched and are not yet connected to this library.

M5 adds generic Change Sets under `src/server/change-management/` and the Admin review workspace at `/admin/review`. Mutations are captured as immutable before/proposed snapshots through closed resource adapters, with optimistic revisions, conflict detection, an append-only event timeline, OWNER-only approval, and atomic publication revisions. Approval never mutates canonical data; only OWNER publication does. The first pilot adapter is `asset.metadata` and permits only Asset `displayName` proposals. Asset bytes remain immutable.

M6 adds an OWNER-only legacy migration workspace at `/admin/system/migration`. M6.1 hardens it with bounded/lazy image scanning: referenced IndexedDB values are read directly, orphan keys are inventoried with a read-only cursor, scan state contains metadata rather than Data URLs/Blobs, and previews/uploads load individual binaries on demand. `IMPORTING` runs resume only after a matching source fingerprint and stage only missing mappings; the first stored snapshot is immutable, an existing `READY` fingerprint is reused, and order diagnostics distinguish invalid, duplicate, and genuinely gapped sequences. Migration runs and diagnostics remain SQLite-backed through `0004_legacy-migration`; no new migration is needed. `FAILED` remains a reserved status with immutable source identity and is not currently produced or resumed automatically.

M7 adds canonical relational models for banners, materials, material appearance settings, tools, navigation, carousel settings, and the runtime source state through `0005_canonical-content`. The canonical baseline is bootstrapped once and idempotently from the approved Admin defaults: 5 banners, 8 materials, 5 tools, 5 navigation items, and the established settings. The current legacy browser content was explicitly classified as disposable test data, so it is not imported and a `READY` M6 run is not required. M6/M6.1 remain available and keep all browser localStorage/IndexedDB/ImageDB data read-only and untouched.

The four Admin content pages now read canonical SQLite data and save only Change Sets through closed adapters. ADMIN and OWNER edits remain invisible until OWNER approval and publication; optimistic revisions and three-way merge prevent silent last-write-wins. Banner and material images reference M4 Asset IDs through a reusable Asset Library picker. The Student uses `/api/content/app`, and the real local product runtime is currently `CANONICAL`. Publishing the earlier cutover created and verified a pre-cutover SQLite backup. Team-management UI is not implemented.

M7.1 restores the specialized canonical Admin editing experience without bypassing Change Sets: banners have a buffered editor, Asset picker, positioning controls, carousel preview/settings, and archive/order operations; materials have stable semantic keys, Asset positioning, live card previews, and shared appearance controls; tools and navigation retain compact editors and live previews. Each page accumulates one local in-memory draft and submits one coherent Change Set. Public canonical payloads expose active banners, available materials, tools including their intentional unavailable/coming-soon state, enabled navigation, and authorized published Asset bytes. The generic Change Set endpoint cannot request runtime cutover; only the dedicated OWNER cutover flow can do so. Existing browser-local content remains untouched.

Canonical tools whose `available` flag is false are intentionally shown as coming soon; that is a product availability state, not a missing backend or legacy-runtime failure.

M8 defines the portable `pythagoras.question-package` V1 contract and bundled Draft 2020-12 JSON Schema under `src/server/question-packages/`. Validation has separate strict structural and semantic stages, recognizes generic/valid/warning/invalid/unsupported JSON states, verifies `subjectKey` against canonical materials, and caches immutable JSON-asset inspection metadata through migration `0006`. Asset Library surfaces package status and diagnostics without changing the uploaded bytes. Student Question Bank placeholders are now subject-scoped and still load no question data. M8 does not add relational question tables, a Question Editor, an importer/converter, search, or publication adapters.

M8.1 hardens that same schema version `1.0.0`: hierarchical order is sibling-scoped, every RichDocument block has a stable UUID, Quran and poetry use shared rich inline spans, tables carry explicit header/presentation semantics, Variants require meaningful content, and per-Variant occurrences preserve `roundCode`, arrays of branches/qualifiers, and a required original `rawLabel`. Question `order` remains canonical; future Student numbering is the local 1-based ordinal after Bank Browse filtering and sorting. Inspector version `2` invalidates older cached results on demand without a database migration.

M9 adds an empty first-class relational Question domain through migration `0007_question-domain` and the internal server module `src/server/questions/`. The M8/M8.1 Package V1 JSON remains the portable import/export contract; canonical SQLite rows become the future mutable source of truth. Packages reference existing canonical Material subject keys, while Taxonomy, Bank Browse, Questions, Variants, per-Variant Occurrences, branches, qualifiers, taxonomy assignments, primary-Variant relations, and Asset bindings are normalized with relational integrity and optimistic revisions. Portable RichDocument image `assetRef` values resolve only to existing Asset Library IDs before canonical persistence. Synthetic materialization is internal and transactional; owned aggregate children intentionally cascade only with their parent Package/Question/Variant/Occurrence, and no destructive route exists.

M9 imports no real Question data and adds no import UI/API, Question Editor, Student Question API, search/FTS, converter, or Quiz Ready architecture. `/admin/questions` and the subject-scoped Student Question Bank remain placeholders. Future Question mutations must integrate with the existing Change Set review and OWNER publication flow before any Student read surface is added.

M10 adds the Rich Content presentation foundation under `src/lib/rich-content/`, `src/components/admin/rich-content/`, and the Student vanilla-JS components/styles. Portable `assetRef`, canonical `assetId`, and public resolved image URLs remain distinct. The Admin React renderer and Student string renderer support all V1 blocks and bold/italic/underline marks with equivalent semantic, RTL, responsive, light/dark-safe output; Quran, poetry, tables, captions, images, and stable block/verse identity are preserved without raw HTML. The public mapper only accepts validated canonical content and injected safe Asset URLs.

M10 adds no editor or Tiptap dependency, no Question API, search, corpus import, or real Question rows. The Student Question Bank remains a subject-scoped placeholder. A future editor must use an adapter that preserves canonical IDs, marks, Asset IDs, and table semantics rather than storing editor-native state.

M11 integrates the relational Question domain with the existing Change Set governance through the registered `question.package`, `question.taxonomy`, `question.browse`, and coherent `question.item` aggregate resource types. Canonical Question tables represent published state only; all human drafts remain in Change Sets. Submission and OWNER approval validate the effective proposed graph but do not mutate canonical rows. OWNER publication applies dependency-ordered Package, Taxonomy, Browse, and Question mutations atomically inside the existing publication transaction, with conservative aggregate conflict detection and stable Variant/Occurrence identities.

Question review reuses the M10 Admin RichDocument renderer for readable before/after wording and answer previews plus compact Variant, provenance, and taxonomy summaries. Package `contentRevision` remains distinct from entity and global publication revisions.

M12 makes Asset Library Question Package import operational. Only `VALID`, or explicitly acknowledged `VALID_WITH_WARNINGS`, packages can stage. The server reopens immutable Asset bytes, verifies integrity, reparses, revalidates the current schema/subjects, resolves manifest assets by SHA-256 metadata, and applies collision checks; the browser submits only an Asset ID and options. Stable portable IDs and `contentRevision` are preserved, `sourceAssetId` records immutable JSON provenance, and manifest `assetRef` bindings are part of the immutable Package proposal.

Import is initial-only and creates one atomic DRAFT Change Set; it never writes canonical Question rows before OWNER publication. Existing active import drafts are reused and already-canonical Packages are reported rather than duplicated. Large Question Change Sets use bounded staging responses and paginated 25-item review with one selected rich preview and resolved taxonomy breadcrumbs. `/admin/questions` is now the Package-level workspace, and manual empty Package creation is governed with a server UUIDv7, `contentRevision = 1`, no source Asset, and no bindings.

M12 imports no real corpus and adds no full Question Editor, Tiptap, search, Student Question API, TXT/OCR converter, or Quiz Ready architecture. Re-import/update is not implemented. M13 has not started.

The prior Question Bank and all real question data remain intentionally removed. Do not add Quiz Ready, MCQ generation, grading, distractors, timers, or attempts. The future relational Question Bank must build on stable IDs, variants with per-variant provenance, one shared answer, rich structured blocks, and Published-only Student reads.

Do not add Firebase, Supabase, or Prisma. Supabase/Postgres is only a future adapter behind repository/storage/search boundaries. Preserve the current Student/Admin UI rather than rebuilding it. New Admin server mutations must derive actor identity from the validated session and apply the shared same-origin mutation protection; never trust an actor ID or role sent by the browser.

Graphify, Understand Anything, Obsidian, Pythagoras-Brain, local AI tooling, and local MCP state are local-only developer tools and must never be committed.
